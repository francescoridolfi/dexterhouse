# ADR-0006: Separate runner service with exclusive Docker socket access

- Status: accepted · Date: 2026-10-31

## Context
Developer and Tester agents must write files, run commands and run tests. The code is generated by LLMs and potentially influenced by third-party packages: it must be treated as hostile. The project owner explicitly chose a runner over mounting the Docker socket in the core.

## Decision
A `runner` service (a Celery worker on a dedicated queue) is the only one with access to the Docker socket. It creates ephemeral `workspace` containers per project and exposes a `workspace` MCP server in them. The core and the agent workers have neither the socket nor access to the workspaces' filesystem.

## Alternatives considered
- Docker socket in the worker: simple, but an RCE in the worker compromises the host.
- In-process execution with `subprocess`: unacceptable.
- Serverless/remote services (E2B, Modal): good, but paid and contrary to self-hosting.

## Consequences
+ Attack surface concentrated in a small, auditable service.
+ Can be scaled or moved to a dedicated host; replaceable with gVisor/Firecracker without touching the agents (decision CD-013).
− Extra latency on every tool call (queue + exec), acceptable for this use case.
− The runner is a single point of failure: health checks and a restart policy.

> Implementation note: each workspace gets its own Docker volume `dh-ws-<id>` (no shared `workspaces` volume) and its own network `dh_sandbox_<id>` (no single shared `dh_sandbox` network). See [security](../security.md).
